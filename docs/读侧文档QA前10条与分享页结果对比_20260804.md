## 1. 结论先行

本轮的“现有读侧管线”复测采用 **Read Runtime v4 active + 非事故基线兼容路径**：

- 10/10 条均完成；
- 10/10 通过本地 v4 verifier；
- 非事故流程/知识 Query 的正式答案由已冻结的 KG_v2 原生读侧提供，v4 负责任务编译、Evidence Fabric、来源快照和校验；答案来源记录为 `read_runtime_v4_non_incident_baseline_compat`；
- 这意味着本轮不是用 v4 的确定性事故编排器重写文档答案，而是避免把完整流程答案误编译为空的“诊断数据中的直接观测”。该兼容边界已在单元测试中固化。

分享页首 10 条 Query 与测试集逐条对齐，共抓到 129 条消息。分享页中第 6、8、10 条是上游服务失败，不代表资料缺失，也不能作为内容质量的负例。其余 7 条有正式回答。

## 4. 逐条观察

### 4.1 已经做得较好的地方

1. **不把分享页上游失败误判为知识缺失。** 第 6、8、10 条分享页只返回“上游服务暂时不可用”，本地仍能独立完成资料召回，说明两条路径的失败域已区分。
2. **图片和附件仍在证据域内。** 第 3、4、5、6、7 条本地答案分别保留了 8、15、47、11、4 个图片标记；不是只输出纯文本摘要。
3. **来源闭包和 Query facet 可观察。** 前 8 条及第 10 条都记录了 `answer_coverage.complete=true`；第 9 条明确记录 `evidence_floor_met=false`、`uncovered_query_facets=["operation:收集"]`，没有伪造蓝屏排查结论。
4. **安全状态没有被答案长度掩盖。** 第 6、8 条虽然有资料，但仍是 `ask_info`，并记录待补日志、IP、网络或最小化测试信息；`answerable` 与 `diagnosable` 没有混为一谈。

### 4.2 当前暴露的通用问题

#### A. 宽召回后的答案编织仍可能过长

第 1 条本地 24 个来源、11676 字符、17 张图，而分享页只保留两个高度相关的角度处理分支。第 5 条本地 23 个来源、15935 字符、47 张图，而 Query 直接问的是 SDK 升级。当前的 `answer_coverage.complete` 只能说明“纳入的证据没有被硬截断”，不能说明“纳入的证据都是回答所必需的”。

后续应增加**答案级证据选择**：先保证 Query 的主操作闭包，再将同文档的背景排查、并列方案和媒体按“直接支持 / 条件支持 / 背景”分层；不能用扩大正文上限代替编织。

#### B. 并列方法需要单独审计

第 4 条本地已经保留多个步骤和图片，但报告只看到了来源数和长度，尚不能证明“方法一/方法二/方法三”均已展开。应在答案 verifier 中增加并列方案覆盖检查：对同级方法标题逐一标记 `expanded`、`risk_controlled` 或 `omitted_evidence_gap`，避免只展开第一条方法。

#### C. 文档召回对语义近邻不够稳

第 9 条的 Query 与分享页蓝屏手册高度匹配，但本地冻结读侧没有正式来源，答案仅 99 字。该问题不是答案编织，而是**文档入口/术语/别名召回没有建立正确的来源闭包**。应优先检查：

- 蓝屏、死机、重启、故障排查等术语是否进入读侧术语表；
- “信息收集”与“排查”两个操作 facet 是否能共同激活同一文档；
- 文档标题或首节命中时是否激活整篇文档；
- SAG 结果与 raw 来源 revision 是否一致。

在这些条件满足前，保持 `evidence_floor_met=false` 是正确的安全行为。

#### D. 分享页的长度不能直接当成标准答案

第 6、8、10 条是上游失败；第 1 条分享页答案只有 218 字符，第 5 条只有 593 字符。分享页适合作为回归对照和人工参考，不应直接作为“越短越好”或“越长越好”的金标准。更合理的评价维度是：主 Query facet 是否闭包、并列方案是否覆盖、每个操作是否有来源锚点、图片是否在需要时呈现、风险动作是否受控。

## 5. KG_v2+raw Codex 独立旁路运行情况

本轮同时启动了独立的 `KG_v2+raw Codex` batch，使用本地 Codex 登录态、`gpt-5.6-luna`、只读工具和 `debug_agent_system.kg_raw_codex.system.v16`。它不是 v4 兼容路径的替代结果。

批次清单：[kg_v2_raw_codex/batch_manifest.json](../data/results/document_qa_first10_20260804/kg_v2_raw_codex/batch_manifest.json)

结果为 **3/10 通过，7/10 在 Codex CLI 调用阶段失败**。成功的是第 1、2、3 条，分别完成 5、6、14 次工具调用；第 3 条读取 7 个文件并暴露 4 个媒体。第 4～10 条的统一失败原因是：

```text
CodexCliAgentError: codex_cli_failed:
You've hit your usage limit for GPT-5.6-luna
```

因此这 7 条没有形成可比较的答案，不能写成“KG/raw 没召回”或“Codex 组织失败”。额度恢复后应从第 4 条断点续跑，并保持相同 prompt 版本和工具审计字段。

## 6. 结论与下一步

当前可确认：

- v4 对文档问答的兼容边界已经修复，10 条不再生成空的事故观测答案；
- 冻结读侧能够对多数 Query 给出可追溯回答，并保留图片和风险状态；
- 真实短板集中在答案级去噪、并列方案覆盖和语义近邻文档召回，而不是简单增加 Top-K；
- Codex 旁路的本轮后 7 条结果被上游额度阻断，不能用来得出内容质量结论。

建议的下一步顺序：

1. 先修复第 9 条的术语/文档入口闭包，并增加该类语义近邻的泛化回归样本；
2. 在 verifier 中落地并列方案覆盖与答案级证据分层；
3. 对第 1、5 条增加“主操作闭包优先、背景资料折叠、媒体按步骤绑定”的通用编织策略；
4. Codex 额度恢复后断点重跑第 4～10 条，再与本地 v4、分享页三方比较。
