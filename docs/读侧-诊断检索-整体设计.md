## 0. 一句话结论

读侧不是绿地：历史 `combined` 管线曾证明确定性路由有效；当前实现已迁移为
`DebugAgentSystem` 独立 runtime。本设计不重做核心，而是在其上形成两条互补链路：

1. **诊断裁决链**：子图锁定 → 三信号遍历 → τ 转诊门控 → 拓扑遍历；
2. **知识回答链**：通用 Query scope → SAG_v2 宽召回 → Evidence Pack → 受证据约束的
   Codex 编织 → 本地校验。

前者负责“能不能诊断、下一步能不能执行”，后者负责“怎样把已经找到的资料组织成高质量
回答”。二者共享证据，但不共享裁决权。

## 1. 主纲：同域 6 论文的五阶段共识

合成笔记的核心共识线（`synthesis §核心发现`）：

> **KG 提供结构化先验 → LLM 解决语义理解 → Agent/遍历做多步推理 → 反馈机制驱动进化**

映到 AOI 读侧（读侧只占检索→遍历→部署三阶段，构建/学习属写侧）：

| 阶段 | 同域最佳实践 | AOI 读侧落点 | 现状 |
|---|---|---|---|
| 检索 | CNC-LLM-KG **子图锁定**（LLM 仅在子图内推理） | 命中 Error 后约束生成范围 | `_route_kg_*` 召回，但生成未严格圈定 |
| 遍历 | CIE-KG-LLM-CNC **GCR 三信号**（因果权重+嵌入+LLM 评分） | 多路检索融合 | BGE+colbert+LightRAG，缺因果边权重 |
| 遍历 | StepFly **拓扑驱动**（DAG Scheduler+Executor） | 沿 `next` 链走，非 LLM 选路 | `next` 条件分支已支持，未用 |
| 转诊 | KG4Diagnosis **τ 阈值 referral** | 置信不足 → 转诊/要数据 | `EscalateToFAE.min_confidence` 已有雏形 |
| 部署 | CNC-LLM-KG 本地 7B + 参数直修 | 现场可行性 | 你已用 qwen，方向一致 |

### 北极星（synthesis 跨主题 #2）

> **「LLM 可以理解和组织，但不能脱离可追溯证据获得诊断裁决权。」**

工业诊断对可靠性要求极高（误诊→撞刀/停机）。LLM 的价值一方面在语义理解、多文档比较
和复杂答案组织，另一方面在辅助评估与验证；但 Variant、BranchRule、Action、安全确认、
充分性和 `verified_fix` 必须由本地 runtime 裁决。这是读侧每个设计决策的最高准则。

### 铁律（StepFly 背书）

**确定性编排在骨架，LLM 只在叶子。** StepFly 的遍历由 TSG→DAG 拓扑决定、Scheduler
只选子任务不选路；KG_v2 的 DiagnosticTrace/BranchRule 就是确定性骨架。绝不把
supervisor、Variant 锁定、安全门和解决态换成 LLM 自由调度。LLM 可以出现在 Tool
选择、日志语义分析、step 相关性评分、Evidence Pack 内的答案组织和输出校验，但只能在
本地提供的证据与状态闭包中工作。

## 2. 目标读侧架构

```
supervisor_input (JIRA/现场/设备上下文 + 可选日志包)
  │
  ▼  [O0 supervisor: DebugAgentSystem.start/step — 已落地, 确定性]
  │   解析 DebugAgentInput, 注入 Equipment/Session 上下文
  │
  ▼  [Q. 通用 Query scope — 已落地, 确定性]
  │   识别实体、文档范围、比较对象、复合操作和用户任务，不生成答案措辞
  │
  ▼  [R. SAG_v2 宽召回 — 已落地]
  │   Variant 通道：Family / Variant / Action / Outcome / BranchRule
  │   Chunk 通道：KnowledgeDocument / Section / FAQ / 表格 / 图片 / 附件
  │   目标是有界高覆盖候选池，不在召回阶段提前完成答案编织
  │
  ├──────────────┐  ← 读侧真正的并行分叉
  ▼              ▼
O-LOG / O-EG       KG_v2 诊断裁决链
日志与调用方资源    A. 子图/Variant 锁定
有界只读解析        B/D. DiagnosticTrace 拓扑遍历
  │                C. answerable / diagnosable / executable
  │                Safety / BranchRule / verified_fix
  └──────┬─────────┘
         ▼
 [P. Evidence Pack Builder — 已落地]
  │  按文档/章节/KG 路径分组，保留原顺序、来源 ID、媒体和 Query facet
  │  默认 6～10 篇文档、40～64 个语义 Chunk；无界全图扫描仅作灾备
  ▼
 [O-GEN. CodexEvidenceAnswerComposer — 已落地、默认关闭]
  │  单次模型调用；只做选择、合并、比较、排序和语言组织
  │  输出 strict answer_sections.source_item_ids，不撰写事实正文
  ▼
 [EA. EvidenceAnswerVerifier — 已落地，本地确定性]
  │  校验 schema、引用闭包、facet 覆盖、unsupported claim、安全与解决态
  │
  ├── 通过 ──> 确定性渲染 answer_sections
  └── 失败/超时/无 API key ──> EvidenceAnswerComposer 确定性降级
         │
         ▼
   回答 + 诊断状态 + sources + required_data + 升级目标
         │
         ▼  [→ 写侧闭环]  DiagnosticSession.matched 记录命中与反馈
```

这套架构刻意不追求“召回时就把最终证据顺序和回答结构全部决定好”。召回层负责
**coverage**，答案组织层负责 **composition**，本地 verifier 负责 **grounding 和
safety**。但宽召回仍有最低契约：真正关键的证据必须进入 Evidence Pack；模型不能补写
候选池之外的知识。

统一 executor 和可选 Codex Tool Harness 已落地。Codex 仅能选择八个白名单 read

仍独占 Variant、BranchRule、Action、安全确认和 verified-fix

### 2.2 2026-07-27 答案组织路线已实现首版

分享 Query 全量结果暴露的主要问题已经从“完全检索不到资料”转向“资料存在但组织不佳”：

- 复合操作只覆盖其中一个子任务；
- 比较问题只展示一个比较对象；
- 多方案或多章节被压成一个长段落；
- 图片与附件脱离对应步骤；
- 相邻但低价值文档挤占正文；
- 为修复单个 Query 不断增加标题和排序规则，泛化成本持续上升。

因此拍板采用：

> **保留通用 Query scope 和 SAG_v2 宽召回能力，把复杂编织交给受证据约束的
> Codex；确定性 Composer 退为默认关闭模型时的离线能力与 fail-open 降级。**

需要注意：

- “单次 Codex Composer 调用”只能组织已经进入 Evidence Pack 的证据；
- 如果希望模型发现缺口后再调用 `retrieve_evidence`，至少需要另一个 Tool round，不属于
  单次答案生成；
- 初期默认 `answer_composer_enabled=false`，先进行离线全量对比和 shadow 验证；
- `EvidencePackBuilder`、单次答案组织器和 verifier 已实现；模拟模型、未知 ID 拒绝、
  缺 key fail-open、真实单 Query 及 47 条完整分享 Query 均已验证；
- 详细输入输出、校验和目标配置见
  [KG_v2读侧主动证据补全与Codex Tool Harness](KG_v2读侧主动证据补全与Codex%20Tool%20Harness.md)。

## 3. 四层同域设计（逐条对接真实模块）

### A. 子图与文档证据域锁定——治幻觉，直击 evidence 虚高

- **依据**：synthesis Stage 2「子图划分后 LLM 仅在子图内推理——精度和幻觉之间的核心折中」。CNC 按报警码锁定因果子图，LLM 不在全图自由发挥。
- **治你的什么病**：eval 铁律 `evidence_recall 97% 但 judge 47%`＝生成没真正落在证据上。把 LLM 生成严格约束在命中 Error 的子图，或 Query scope 直接命中的文档证据域内，是治幻觉的核心一刀。
- **落点**：诊断型 Query 使用 `Family → Variant → DiagnosticTrace → Action/BranchRule` 闭包；知识型 Query 使用 `KnowledgeDocument → KnowledgeSection → Chunk/Media` 闭包；混合 Query 同时提供两组证据，但明确区分“文档说明”和“本次现场诊断”。

### B. GCR 三信号遍历（CIE-KG-LLM-CNC）——治精度

- **依据**：synthesis Stage 3 称其为「最精确的遍历策略」＝**因果强度边权重 + 图嵌入 + LLM 置信度评分**三重融合。
- **治你的什么病**：你现在是 BGE+colbert+LightRAG，缺**边上的因果强度权重**这一路结构化信号。
- **落点**：把读写共用的「自进化权重」（路线图④）作为遍历的第三路信号——权重不只给写侧排序，也参与读侧选路。与 `retrieval.fuse_results` 的多路融合天然契合。

### C. τ 转诊门控（KG4Diagnosis）——治「硬答」，含升级 agent

- **依据**：synthesis Stage 3「GP 初诊→置信度不足→referral 到专科」，**τ=0.7 触发跨层级转诊**。
- **治你的什么病**：信息不足也硬答（evidence 虚高的根因之一）。
- **落点（两处）**：
  - **入口充分性门控**：路由前判「够不够诊断」，不够 → 触发 `required_info_schema`（schema 已有槽位）要数据，而非硬答。参考 Self-RAG 的 retrieve-or-not。
  - **出口升级 agent**：把 `_resolve_escalation_target` 从被动函数升为主动 agent——自服务走到死胡同时，按 `escalation_target` enum 判定升级团队并打包现场证据。对接 `submission-criteria.json` 的 `EscalateToFAE.min_confidence`（现 0.3，可校准到 τ）。

### D. 拓扑驱动遍历（StepFly）——治 check_recall

- **依据**：synthesis Stage 3「拓扑决定遍历」＝TSG→DAG，Scheduler 选子任务 + Executor 执行，不靠 LLM 选路。
- **治你的什么病**：`check_recall 45%` 偏低——LightRAG 靠 prose 综合，检查易被改写糊掉。
- **落点**：命中 Error 后**沿 `next` 条件边一步步走**（你 schema 的 `next` 带 condition 分支已支持，现 `~95% Error 单 Check` 没用上），出 Check→拿反馈→按 condition 分支。把 check_recall 从「碰运气蹭中」变「结构保证命中」。写侧长出分支后，这是唯一吃到分支红利的消费者。
- **交互形态：多轮对话（已定 2026-06-25）**，详见 §3.1。
- **顺带**：可替掉 `_filter_steps_for_query` 那 290 行工控机硬编码——「哪些 step 跟 query 相关」从硬编码改成数据驱动的 step-relevance 打分（LLM 只做叶子打分，符合铁律）。

### 3.1 多轮对话遍历协议（D 的人机交互，已定）

D 遍历**做成多轮对话**（CNC-LLM-KG 同款），而非一次性吐整链。这把读侧从「request→response」抬成「有状态会话」，并强制带出三处下游变更。

**状态机**（O0 supervisor 驱动，确定性，符合 I1）：

```
INTAKE   O0 解析输入 + MEM 建 DiagnosticSession + C 充分性门控
   │        信息不足 → ASK_INFO(required_info_schema) → 循环直到够
   ▼
LOCATE   O-KG 检索 + A 子图锁定命中 Error；O-LOG 的 skip_list 预跳「日志已确认」的 Check
   │
   ▼
STEP     D 取 next 链上的下一个 Check；O-GEN 把 how_to_check 渲染成一句提问
   │
   ▼
AWAIT    等用户/日志回结果
   │
   ▼
BRANCH   按 next 的 condition 评估结果；MEM 记 (check, result) 并更新 ruled_out
   │        未解 → 回 STEP 下一个；命中 Solution → RESOLVE；无路可走 → ESCALATE
   ▼
RESOLVE  应用 resolved_by Solution；★ EA 校验结论落在证据上；记 which_check_solved
ESCALATE 链尽/死胡同/反复要不到数据 → O-ESC 按附表1 负责人升级 + 打包证据
```

> I8 安全约束：进入 RESOLVE 前，若 Solution 是破坏性操作（停机/拆机），必须显式人工确认，不自动执行。

**变更 1 — O0 supervisor 契约从单发改为有状态**：`diagnose_from_supervisor(input)→result` 升级为会话式 `start(input)→{session_id, first_check}` + `step(session_id, user_response)→{next_check | resolution | escalation}`。对应 MCP 的 `interactive:true` 路径（`Agentic方向.md §5` 的 `diagnose` tool 已留 `interactive` 参数）。**保留 `interactive:false` 单发路径**作批处理/eval 回退。

**变更 2 — MEM 从可选升为必需**：多轮必须持久化会话状态。`DiagnosticSession` 记 `current_check / checks_presented[] / check_results[] / ruled_out[] / which_check_solved / status`（沿用 schema，不改 ontology）。

**变更 3 — 写侧获得「按 Check 回写」的富信号**：单发只产 Error 级 `matched`；多轮产**每步**结果——哪个 Check 做了、结果如何、`which_check_solved`。这正是 W5 ATR 提权（给解题的那条 `resolved_by` 边加权）和未来 PRM 信用分配（区分「高价值中间步骤」vs「dead end」）的数据来源。读→写闭环因此从 Error 级细化到边级。

当前安全落地：`src/debug_agent_system/eval/debug_sim` 产生可观测 run；`src/debug_agent_system/agents/loop/diagnostic_feedback` 将会话反馈转成 review_queue 候选；默认不直接修改 KG 主图。

**eval 连带（I2）**：多轮回归由 `src/debug_agent_system/eval/debug_sim/runner.py` 驱动；当前 100 例 stateful eval 已可运行。后续若引入 LLM simulator，必须加 verifier，不能替代 deterministic simulator 作为门禁。

### ★ EA：诊断与答案证据校验

- 在 composer 之后执行「结论-证据对齐」校验：答案每个条目是否真落在绑定的
  `evidence_ids/chunk_ids` 上，不落则删除、降级或回到确定性 Composer。
- 除 relevance 外，EA 还必须检查 Query facet 覆盖、未知来源 ID、媒体绑定、安全状态和
  `verified_fix`。这使 Codex 能够负责复杂语言组织，但不能扩大运行时裁决。

## 5. 读↔写闭环（multi-agent system 的真正价值）

两侧连起来才成系统（synthesis 跨主题 #1「数据闭合度＝系统自主性上限」）：

- **读→写**：每次 `DiagnosticSession` 记录「命中哪个 Error、用户反馈解没解决」。解决了 → 写侧 `occurrence_count++` 提权重（GraphMind ATR）；没解决 → 进 `data/kg/review_queue` 当新证据。当前由 `agents/loop/diagnostic_feedback` 负责把会话反馈转成人工候选。
- **写→读**：日志分析在读侧反复见到、KG 没有的报错模式 → Drain3 反向挖 `LogPattern`（路线图⑤，现 0 实例）→ 经写侧入图 → 下次读侧 `maps_to` 边直接命中。

> synthesis 的结论「**CNC-LLM-KG 的半闭环是当前工业场景最优解**」（自动化不可全交给统计，人工不可规模化）支持你的取舍：读侧自动诊断 + 写侧 review_queue 人工把关，不追求 GraphMind 式全自动。

## 6. eval 纪律（贯穿所有读侧改动）

**每个新子 agent/层上线前，必须先在评测上证明它改善了 coverage、judge 或
check_recall，且没有破坏 grounding 与 safety，动不了就不加。**

LLM 答案组织层不能只看“读起来更自然”，必须同时报告：

- Evidence Pack 的文档、Chunk 和 Query facet 覆盖；
- `unsupported_claim`；
- `source_attribution`；
- `useful_answer_before_question`；
- `refusal_with_relevant_evidence`；
- 比较对象覆盖率、复合子任务覆盖率、多方案分点完整率；
- 图片/附件与步骤绑定准确率；
- 未知证据 ID、高风险动作绕过和错误 `verified_fix` 声明；
- 模型调用成功率、超时率、校验失败率和确定性降级率；
- token、时延和单次答案成本。

评测必须使用完整分享 Query 集输出确定性版与 LLM 版逐项对比，不能只挑代表集。模型版
未通过 verifier 时仍保存原始输出和明确失败原因，但线上返回确定性降级答案。
