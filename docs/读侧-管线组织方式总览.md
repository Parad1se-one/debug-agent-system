# 读侧管线组织方式总览

> 更新时间：2026-08-04
> 范围：`debug_agent_system` 的冻结 KG_v2 原生读侧、可选 Incident Evidence Runtime、
> 独立 KG_v2+raw Codex 旁路、Read Runtime v3 shadow 和 Read Runtime v4 证据调查管线；
> 不包含写侧知识抽取、审核和入图。
> 目的：用一份文档说明一次 Query 如何进入系统、如何召回证据、如何完成诊断裁决、如何
> 组织答案，以及各阶段由确定性代码还是 Codex 负责。

## 1. 一句话描述

当前读侧保留冻结主链、案件证据扩展和独立 Agent 旁路，并用 v3/v4 运行时将它们
适配到统一证据契约：

```text
                         ┌─ 冻结基线：SAG → KG Runtime → Composer
Query / 会话上下文 ──────┼─ 诊断包扩展：时间 Scope → Artifact 窗口 → Incident Evidence Pack → verifier
                         ├─ 独立旁路：Codex Agent（API 或本地登录态）→ verifier
                         ├─ v3 shadow：统一 Task → Evidence Fabric → Planner → Policy → Verifier
                         └─ v4 调查：InvestigationState → 行动计划 → Policy → Verifier
```

v3 shadow 默认不替换上述任一正式输出。它先调用冻结基线得到官方回答，再将
KG/SAG、raw、Incident 和请求携带的日志/源记录归一为 EvidenceRecord，产生
`shadow.proposed_answer`及差异审计。仅当未来显式关闭 shadow、Answer Plan 通过本地门禁
且达到分层发布指标时，才允许逐场景接管。

Read Runtime v4 是在 v3 Evidence Fabric 之上的增量调查运行时。它不改写冻结 v3
契约，也不新增顶层行动对象，而是把 `next_tests` 规范化为带风险、优先级、前置条件、
回滚和来源锚点的行动记录，并按“立即保全、诊断验证、候选修复、修复后验证”编译答案。
v4 默认同样处于 shadow；显式 `--active` 只切换经过本地 verifier 的答案，不授予设备
执行权限。事故 Query 有诊断包时，v4 以时间对齐后的 Incident Evidence 为主证据，
不会把无关文档步骤混入案件结论。

对没有诊断包的流程/知识 Query，v4 当前使用
`read_runtime_v4_non_incident_baseline_compat`：保留已通过冻结读侧校验的完整答案，
同时执行 v4 的任务编译、Evidence Fabric 和 verifier，不把流程答案误标成“诊断数据中的
直接观测”。这是一条可回滚的兼容边界，不代表 v4 已经接管文档问答的答案编织；后续
接入 procedure Planner 后，仍需在同一证据契约下单独通过并列方案、媒体和来源闭包评测。

冻结基线采用“**宽召回证据、确定性裁决、受约束编织、本地校验**”的组织方式：

```text
Query / 会话上下文
        │
        ▼
通用 Query scope
        │
        ▼
SAG_v2 Variant + Chunk 双通道宽召回
        │
        ├────────────────────┐
        ▼                    ▼
文档证据域               KG_v2 诊断证据域
        │                    │
        │               Variant / Trace / Branch / Safety
        └─────────┬──────────┘
                  ▼
         answerable / diagnosable / executable
                  │
                  ├── 缺现场证据或 required_data 未满足
                  │
evidence_resources（日志、DMP、文档、Jira、proj、图片、附件）
                  │
                  ▼
         Evidence Gap Resolver
                  │  根据 required_data 选择资源和 parser
                  ▼
      ReadEvidenceToolExecutor（统一只读 Tool 契约）
                  │
       ┌──────────┼──────────┬──────────┬──────────┐
       ▼          ▼          ▼          ▼          ▼
 log_package     dmp      document     jira       image
   parser       parser      parser      parser     parser
       │          │          │          │          │
       └──────────┴──────────┴──────────┴──────────┘
                  │  attachment/proj/context 等 parser 同样接入
                  ▼
  source-bound observations + tool-evidence + excluded reasons
                  │
                  └──> 重新进入 Query scope / SAG_v2 / 充分性判断
                                      │
                                      ▼
                               Evidence Pack
                                      │
                      ┌───────────────┴────────────────┐
                      ▼                                ▼
             Codex 调查工具循环                 Codex 单次答案编排
  retrieve / expand / KG / assets / parse              │
                      │                                │
                      └──── render_evidence_answer ────┘
                                      │
                                      ▼
                             本地 Answer Verifier
                                      │
                           ┌──────────┴──────────┐
                           ▼                     ▼
                       校验通过              失败/超时/未启用
                           │                     │
                           │          确定性 EvidenceAnswerComposer
                           └──────────┬──────────┘
                                      ▼
                AgentResponse + answer_sections + sources + metadata
```

可选的 `CodexReadToolHarness` 位于入口外层。它通过 strict Tool 使用确定性诊断、
Variant/Chunk 召回、整篇文档展开、KG 路径检查、图片/附件检查和资源解析；调查结束后，
只能调用 `render_evidence_answer` 提交 Evidence Pack 内的条目 ID。真正的数据读取仍由
本地 executor/parser 完成，Codex 不直接读取任意文件。

Jira 问题描述、粘贴日志或诊断包进入可选 `IncidentEvidenceRuntime`。该层不会把整包文本
压平成 Query，而是先把参考时间规范成独立窗口，再流式抽取对应日志，建立 artifact manifest、
事件、调用栈、环境、时间线、异常后重启/跨日期复发相关性、案件图、KG 稳定锚点、假设矩阵
和下一步测试，产出 `incident_evidence_pack.v3`。它默认关闭；shadow
mode 只写 metadata，不改变冻结基线答案。详见
[读侧 Jira 诊断数据包与 Incident Evidence Runtime](读侧-Jira诊断数据包与Incident-Evidence-Runtime.md)。

新 `KG_v2+raw Codex` 旁路位于 `src/debug_agent_system/kg_raw_codex/`。它不接入
`DebugAgentSystem.start()`，也没有自制 Top-K、相关性分数或领域检索规则。它支持两种
显式运行载体：非流式 Responses API 使用 `.env.local` 和无排序的
`list_files`、`search_text`、`read_text`；本地 Codex 使用登录态和受 read-only sandbox
约束的 `rg --files`、`rg`、`sed`。两者都由 Codex 自主规划搜索、迭代读取和回答组织，
共用 required facets、Prompt、结构化输出和本地 verifier，失败时不会静默互换。
术语解析结果只作为调查上下文，不决定候选文件或 Top-K。

本地登录态模型通过批次参数显式指定，模型并不是管线逻辑的一部分。2026-08-03 的第
6–10 条复测中，第 6–8 条使用 `gpt-5.3-codex-spark`，第 9–10 条在用户明确允许后改用
`gpt-5.6-luna`；两组仍经过同一 v14 Prompt 和 verifier，但跨模型结果不作为严格同模型横评。
本地程序不参与相关性排名，只校验 Query facet、实际读取来源、路径边界和图片路径。
详见
`docs/读侧冻结与KG_v2+raw Codex新管线.md`。

其中：

- 检索层负责找到足够广、可追溯的候选证据，不负责提前写好最终答案；
- KG_v2 runtime 负责 Variant、诊断计划、分支、安全和解决态；
- Codex 只负责在 Evidence Pack 内选择、合并、比较和排序；事实正文仍由本地渲染；
- 本地 verifier 负责保证每条回答有来源、不越权、不绕过安全门；
- 没有 Codex 或模型失败时，系统仍可使用确定性 Composer 独立运行。

## 2. 三个核心平面

### 2.1 证据面：回答“资料在哪里”

证据面由 Query scope、SAG_v2、KG_v2 原图和只读资源解析器组成。

主要职责：

- 分解 Query 的主题、实体、文档范围、比较对象和复合操作；
- 从 FaultVariant、Family、Action、Outcome、BranchRule 中召回诊断候选；
- 从 SOP、手册、FAQ、表格、案例中召回原文 Chunk；
- 保留源文档标题、章节层级、原始顺序、offset、hash、图片和附件；
- 对调用方提交的日志、DMP、Jira、proj、图片等执行有界只读解析；
- 记录被排除材料及原因。

证据面不决定：

- 哪个 Variant 已经被锁定；
- 哪个现场动作可以执行；
- 问题是否已经解决；
- 最终答案应该采用什么措辞。

### 2.2 裁决面：回答“现在能判断和执行到什么程度”

裁决面由本地 KG_v2 runtime 完成，是整个读侧的确定性骨架。

主要职责：

- 对 FaultFamily/FaultVariant 候选进行阈值和 margin 判断；
- 锁定 Variant，或保持 `document_answer_only`；
- 编译 DiagnosticTrace、TraceStep、DiagnosticAction 和 BranchRule；
- 根据用户反馈选择后续分支；
- 判断 RequiredInfo 是否真正影响候选区分、分支选择或安全执行；
- 执行高风险动作人工确认门；
- 只有 `verified_fix` 被现场反馈激活时才进入 `resolved`；
- 维护多轮 `DiagnosticSession`。

裁决面输出三个互相独立的充分性结果：

| 结果 | 含义 |
|---|---|
| `answerable` | 当前证据足以回答资料中已经明确的内容 |
| `diagnosable` | 已锁定 Variant，并编译出 KG_v2 诊断计划 |
| `executable` | 当前动作满足分支上下文和安全前置条件，可以继续执行 |

因此 `ask_info` 不等于拒绝回答。系统可以同时满足：

```text
status=ask_info
answerable=true
diagnosable=false
executable=false
```

此时应先回答已经检索到的文档知识，再提出真正必要的问题。

### 2.3 组织面：回答“怎样把证据变成可读答案”

组织面不拥有诊断裁决权，只消费证据面和裁决面的结果。

当前状态：

- `EvidenceAnswerComposer` 已实现；
- 它按固定章节确定性组织事实、诊断步骤、条件、未知项、追问和来源；
- 它保证离线可用和来源绑定；
- `EvidencePackBuilder` 已实现并在每次响应中生成结构化 Evidence Pack；
- 可选 `CodexEvidenceAnswerComposer`、`CodexReadToolHarness` 和本地 verifier 已实现；
- 直接 Composer 每个答案最多调用一次；Tool Harness 最多 3 轮；
- 模型只返回 strict `answer_sections.source_item_ids`，可在内容章节间重组，但不撰写正文、
  不移动不确定性/追问、不控制状态；
- 本地 `EvidenceAnswerVerifier` 校验后再渲染；
- 失败时回退到现有确定性 Composer。

冻结基线默认仍关闭 Codex 答案组织，保证无网络时可独立运行。其 2026-07-30
`gpt-5.3-codex` 对比运行是历史基线，不代表新 KG_v2+raw 旁路仍使用同一调用方式。
该历史基线曾对纯 Codex 分享页 47 条 Query 完成同集全量复跑。

- Evidence Pack 47/47，可追溯正文证据门槛 42/47；
- Codex Composer 调用 42/47、采用 40/47；
- 2/47 因瞬时传输错误确定性降级，5/47 因没有正文证据而不调用模型；
- Query 子任务证据闭包与客观运行门禁为 38/47；
- 通用追加追问 0，直接暴露磁盘/引导命令 0，高风险细节命中 0。

38/47 是结构化证据与安全门禁结果，不是语义正确率。剩余 9 条中，5 条为主板手册尚未
进入可批准 Chunk 索引，4 条为“备份、逐条测试、更换规格、双版本处理”等子任务尚未
建立完整证据闭包；这些缺口不会交给 LLM 自由补写。

### 2.4 KG_v2+raw Codex Agent 独立旁路

新旁路的组织面和调查面由同一个 Codex Agent 完成：

```text
                   临时只读 corpus workspace
                  ┌──────────────────────────┐
Query + facets ──>│ data/raw                 │
                  │ data/kg_v2               │
                  │ data/extracted_docx      │
                  └────────────┬─────────────┘
                               ▼
              ┌─ Responses API / gpt-5.4 / 函数工具
              └─ Codex CLI / gpt-5.3-codex-spark / 只读 shell
              计划 → 函数搜索 → 阅读 → 再搜索 → 编织
                               │
                               ▼
       answer_markdown + coverage_ledger + procedure_variant_ledger
                         + files_read
                               │
                               ▼
           本地边界/来源/facet/媒体 verifier → 审计产物
```

这里没有自制 BM25/分词排名、预设 Top-K 或领域专用检索规则。Codex 决定如何调用
`list_files`、`search_text`、`read_text` 以及读哪些文件；本地代码只提供通用只读
文件访问、格式展开、语料边界和不可绕过的发布校验。API 载体从 `.env.local` 认证；
CLI 载体从本机 Codex 登录态认证，并以 `--ephemeral --ignore-user-config --ignore-rules`
运行。两者都只允许读取临时语料工作区，不允许联网或写文件。

独立旁路的完整生命周期是：

1. 从 Query 生成 `required_facets`、`ANSWER_SCOPE` 和术语上下文；
2. 把 `data/raw`、`data/kg_v2` 与 DOCX 确定性展开视图装入临时只读工作区；
3. Codex 自主规划、搜索、阅读，并形成 `answer_markdown`、`coverage_ledger`、
   `procedure_variant_ledger`、`files_read`；
4. 本地统一校验 schema、真实读取审计、双证据域、facet 闭包、来源、媒体、安全命令和
   v15 多分支标题/步骤层级；对于实际用于闭包 Query 的 raw 来源，还会从原文独立识别
   “方案一/二/三”“方法一/二/三”等同级路径，执行并列方案覆盖检查；
5. 首稿不合格时把错误反馈给 Agent 并完整重试；达到预算仍失败则只产出失败审计，不发布
   草稿；
6. 通过后物化图片、写入回答 JSON、batch manifest，并由报告生成器纳入横向对比。

并列方案门禁与 facet 门禁解决的是不同问题：facet 门禁确认“用户任务至少有证据”，
并列方案门禁确认“同一份答案证据中明确列出的替代路径没有被模型静默删掉”。每条原文
方案必须在答案标题和 `procedure_variant_ledger` 中同时标记为以下一种状态：

- `已展开` / `expanded`；
- `风险受控地展示` / `guarded`；
- `因证据缺失而省略` / `omitted_evidence_gap`。

三个 `allow_*_commands` 只分别约束系统修复、引导修复和破坏性磁盘命令，不是所有
命令的总开关。直接完成用户请求、原文可追溯且非破坏性的命令允许展示。外部脚本或
安装包也不再静默消失：原文链接可以保留；若脚本内容、版本、哈希未核验，必须标为
“风险受控地展示”，披露审计缺口，并优先推荐可审计的系统内置方法。

## 3. 一次 Query 的完整生命周期

### 阶段 0：入口与会话

入口：

```python
DebugAgentSystem.start({
    "query": "...",
    "interactive": True,
    "session": {},
    "chat_history": [],
    "log_summary": {},
    "routing_context": {},
    "evidence_resources": []
})
```

多轮推进：

```python
DebugAgentSystem.step(
    session_id,
    user_message,
    evidence_resources=[]
)
```

`interactive=true` 进入有状态诊断循环；`interactive=false` 使用同一检索和裁决核心，但一次
返回当前能够提供的完整答案。

### 阶段 1：通用 Query scope

`knowledge_v2/query_scope.py` 先把自然语言 Query 转换成检索约束和可审计任务模型。
当前任务契约为 `debug_agent_system.query_task.v2`，例如：

```json
{
  "entities": ["DDU"],
  "objects": ["显卡驱动"],
  "operations": ["卸载", "安装"],
  "context_operations": ["排查"],
  "conditions": [{"condition_id": "can_enter_system"}],
  "sequence": [
    {"before": "彻底卸载旧驱动", "after": "重新安装驱动"}
  ],
  "comparison": {"active": false, "objects": [], "dimensions": []},
  "versions": [],
  "deliverable": "procedure",
  "subject_domains": [],
  "facets": []
}
```

Query scope 的目的不是写规则答案，而是避免以下错误：

- 知识查询被相邻故障 Variant 抢占；
- 比较 Query 只保留一个对象；
- “卸载并安装”只覆盖安装；
- 强实体 Query 被通用主板、软件或案例替代；
- “可以进入系统”和“无法进入系统”等互斥条件混入同一证据域。
- “内存占用卡顿”和“物理内存完整性检测”因共享“内存”一词而串证据。

Query scope 必须保持通用，不允许按某个 Query 完整句子增加特判。

### 阶段 2：SAG_v2 双通道宽召回

SAG_v2 是 KG_v2 的可重建 SQLite serving index，不是第二事实源。

两条召回通道：

| 通道 | 召回对象 | 用途 |
|---|---|---|
| Variant 通道 | Family、Variant、Action、Outcome、BranchRule | 诊断候选和计划 |
| Chunk 通道 | Document、Section、FAQ、表格、图片、附件 | 知识回答和证据补充 |

召回阶段保留：

- 原始检索分数和最终相关性分；
- 候选分数构成；
- top margin；
- seed 到 Variant 的 KG 路径；
- supporting chunks；
- 直接命中文档；
- fallback 和灾备状态；
- 排除原因。

宽召回是有界的。常规目标是让相关证据进入候选池，不是在这一阶段确定最终正文顺序。
无界 JSON 全图扫描只允许作为明确标记的灾备路径。

### 阶段 3：证据域形成

读侧形成两类可以并存的证据域。

文档证据域：

```text
KnowledgeDocument
  └─ KnowledgeSection
      └─ Chunk / Table / FAQ / Media
```

诊断证据域：

```text
FaultFamily
  └─ FaultVariant
      └─ DiagnosticTrace
          └─ TraceStep
              ├─ DiagnosticAction
              ├─ BranchRule
              └─ Outcome
```

孤立但高相关、已批准且可追溯的原文 Chunk 可以进入知识回答，但不能生成执行动作。只有
KG_v2 诊断证据域中的 Action 才能进入诊断计划。

### 阶段 4：候选锁定与充分性判断

运行时根据分数、margin、Trace、Evidence 和 Query scope 决定：

- `kg_v2_locked`：锁定 Variant，可以编译诊断计划；
- `document_answer_only`：有文档可以回答，但不能锁定现场故障；
- 未命中可靠证据：只返回当前能够确认的边界和必要追问。

锁定 Variant 后，运行时从 KG_v2 编译计划，不允许 Codex 自行挑选 Action。

### 阶段 5：Evidence Gap 主动补全

如果状态是 `ask_info`，并且调用方已经提供相关资源：

```text
required_data
      │
      ▼
EvidenceGapResolver
      │
      ▼
ReadEvidenceToolExecutor
      │
      ▼
source-bound observations
      │
      ▼
重新检索和充分性判断
```

这一层只读取和归一化证据：

- 默认最多 2 轮；
- 默认最多 12 个资源；
- 每个资源最多读取 65536 bytes；
- 相同调用 fingerprint 不重复解析；
- 图片当前只读元数据，不做 OCR；
- observation 不等于根因；
- Tool 不能执行 Action、修改 KG 或激活 `verified_fix`。

### 阶段 6：Evidence Pack（已落地）

`EvidencePackBuilder` 将宽召回候选整理成给答案组织器使用的
`debug_agent_system.answer_evidence_pack.v2`：

```text
query_scope
runtime_decision
document evidence groups
KG diagnostic trace
tool observations
required_data
allowed evidence/chunk/media IDs
grounded evidence floor
required / optional / excluded source items
```

当前预算：

- 最多 8 篇候选文档；
- 最多 64 个语义 Chunk；
- 最多约 60000 输入字符；
- 优先保证 Query 子任务覆盖，再考虑单个 Chunk 的最终分数。

三层选择策略：

- `required`：安全条件、Action/Outcome、RequiredInfo，以及每个 Query facet 的最佳证据锚点；
- `optional`：已批准且可追溯，允许 Codex 选择、合并或省略的补充事实；
- `excluded`：弱候选、无来源、未批准、重复、安全过滤或对象域不兼容的材料，并记录原因。

`mandatory` 只作为 `required` 的过渡兼容镜像。Evidence Pack 必须至少含一条批准且
可追溯的正文证据，才满足 `evidence_floor_met`；单独的候选名称、检索分数或运行时状态
不能充当回答证据，也不能使 Query facet 通过。

Evidence Pack 保留文档和章节顺序，不把所有 Chunk 拼成无结构长文本。超过预算时直接
跳过 LLM 组织并使用确定性答案，避免在没有覆盖保证的情况下截断关键子任务。

### 阶段 7：Codex 调查与受约束编织（已落地、默认关闭）

Codex 可以完成：

- 从 `optional` 证据中删除弱相关条目，只保留围绕 Query 的内容；
- 多文档事实合并；
- 比较对象分别说明；
- 复合子任务完整覆盖；
- 多方案独立分点；
- 不同条件和冲突资料分别组织；
- 图片和附件放回相应步骤；
- “先回答、后追问”的语言编排。

Codex 不能完成：

- 补写 Evidence Pack 外的事实；
- 切换 Variant 或诊断计划；
- 决定高风险动作可以执行；
- 将 `ask_info` 改成 `resolved`；
- 在没有 `verified_fix` 时宣称已经解决；
- 生成或改写事实正文。

输出为严格结构：

```json
{
  "answer_sections": [
    {
      "section_type": "document_guidance",
      "source_item_ids": [
        "answer-item:..."
      ]
    }
  ],
  "covered_query_facets": [],
  "uncovered_query_facets": []
}
```

### 阶段 8：本地校验

本地 verifier 至少执行：

1. JSON schema 校验；
2. `source_item_id` 闭包校验；
3. Query facet 覆盖声明校验；
4. evidence floor 与至少一条 grounded item 校验；
5. `required` 条目完整性校验；
6. section 与本地条目类型兼容性校验；
5. 合格必选事实不得被静默删除；
6. `required_info` 必须位于已有回答之后；
7. 最终正文、来源和媒体只从本地 canonical 条目恢复。

失败、超时、缺少 API key 或模型未启用时，不进行第二次自由生成，直接使用确定性
`EvidenceAnswerComposer`。

### 阶段 8.5：导航证据缺口显式化

如果 Query 的必需 facet 尚未闭包，但实际召回的 Chunk 已包含与该 facet 匹配的
子文档导航入口，`navigation_evidence_gap` 会在 Codex 编织和 verifier 之后生成
确定性的“资料缺口”：

- 说明系统已经看到哪个子任务入口；
- 绑定父文档、Chunk、relationship ID、目标 URL 和 wiki token；
- 区分“子文档未入索引”与“子文档已入索引但本轮未召回”；
- 不把目录名当正文，不补写缺失步骤；
- 将结构化缺口写入 `metadata.answer_coverage.navigation_evidence_gaps`。

这一层放在模型之后，保证 Codex 即使没有主动描述缺口，最终回答也不会静默遗漏
用户已经明确提出的子任务。

### 阶段 9：响应渲染

统一输出 `AgentResponse`：

```json
{
  "schema_version": "debug_agent_system.response.v2",
  "session_id": "...",
  "status": "ask_info",
  "answer": "由 answer_sections 确定性渲染的文本",
  "required_data": [],
  "family_id": "",
  "variant_id": "",
  "plan_id": "",
  "current_action_id": "",
  "evidence_ids": [],
  "answer_sections": [],
  "sources": [],
  "metadata": {
    "query_scope": {},
    "retrieval": {},
    "sufficiency": {},
    "answer_coverage": {}
  }
}
```

`answer` 是兼容字段，必须从通过校验的 `answer_sections` 确定性渲染。QA adapter 或上游
Supervisor 不得再次无来源改写正文。

## 4. 三类主要运行路径

### 4.1 文档知识问题

```text
“如何进入安全模式”
  → knowledge lookup
  → 命中 Windows 文档及相关章节
  → document_answer_only
  → answerable=true
  → 组织完整文档步骤和图片
  → 不要求先锁定 Variant
```

### 4.2 现场故障诊断

```text
“板子到达进板口，皮带不转”
  → fault diagnosis
  → Variant 候选满足分数和 margin
  → kg_v2_locked
  → 编译 DiagnosticTrace
  → 根据 RequiredInfo 和 BranchRule 判断首步
  → 返回 step 或 ask_info
```

### 4.3 有资料但现场信息不足

```text
“开机后一直转圈无法进入系统”
  → 直接命中文档
  → 相邻 Variant 仍有歧义
  → answerable=true
  → diagnosable=false
  → executable=false
  → 先给出安全模式/修复路径等资料
  → 最后追问当前界面和现场表现
```

## 5. 状态机

```text
start
  │
  ├─ 有文档、无可靠 Variant ──> ask_info / document_answer_only
  │
  ├─ Variant 已锁定、首步可执行 ──> step
  │
  ├─ Variant 已锁定、缺分支或确认 ──> ask_info
  │
  ├─ verified_fix 被激活 ──> resolved
  │
  ├─ 诊断链尽或超过轮次 ──> escalate
  │
  └─ 会话或 KG 上下文失效 ──> failed
```

关键约束：

- `resolved` 必须 fail-closed；
- 临时恢复、待观察和无证据口头反馈不能进入 `resolved`；
- 高风险 Action 必须先人工确认；
- 多轮达到 `max_turns` 后升级，不无限循环；
- 知识型文档回答可以完整输出，但不会伪装成现场根因。

## 6. Codex 在管线中的两个位置

### 6.1 Tool Harness：已经实现

`CodexReadToolHarness` 可以选择八个白名单 Tool：

- `diagnose_start`
- `diagnose_step`
- `retrieve_evidence`
- `expand_document_context`
- `inspect_kg_path`
- `inspect_source_assets`
- `parse_evidence`
- `render_evidence_answer`

前七个工具负责调查，最后一个工具负责提交封闭答案计划。`render_evidence_answer`
只接受当前会话 Evidence Pack 中的 `source_item_id`，经本地 verifier 通过后恢复正文；
它不能改变状态、Variant、BranchRule、Action 或安全门。

### 6.2 答案 Composer：已经实现、默认关闭

`CodexEvidenceAnswerComposer` 负责“怎样组织 Evidence Pack 中已经存在的证据”。

两个位置相互独立：

- Tool Harness 可以关闭，答案 Composer 也可以单独关闭；
- Tool Harness 可能包含多个 Tool round；
- 答案 Composer 每个答案最多一次模型调用；
- 二者都不能获得安全、执行或解决态裁决权；
- 二者失败时都必须 fail-open 到确定性 runtime。

## 7. 降级与故障隔离

| 故障 | 系统行为 |
|---|---|
| Codex 未启用 | 使用确定性 Composer |
| 缺少 `OPENAI_BASE_URL/OPENAI_API_KEY` | 使用确定性 Composer，记录降级原因 |
| Codex 超时或网络失败 | 使用确定性 Composer |
| 模型输出不是合法 JSON | 本地拒绝，使用确定性 Composer |
| 模型引用未知证据 ID | 本地拒绝，使用确定性 Composer |
| Evidence Pack 没有关键证据 | 明确记录 uncovered facet，不允许模型补写 |
| SAG revision 不一致 | 非 snapshot 模式从 KG_v2 重建；snapshot 模式 fail-closed |
| 会话引用的 KG 上下文失效 | 返回 `failed/invalid_kg_v2_session` |
| 高风险动作缺人工确认 | 保持 `ask_info` |
| 没有 verified fix | 不进入 `resolved` |

## 9. 观测与评测

每次响应至少保留：

- Query scope；
- Variant/Chunk 候选及分数组成；
- top margin；
- KG 检索路径；
- supporting chunks；
- fallback 状态；
- `answerable/diagnosable/executable`；
- eligible/included/excluded evidence；
- Evidence Gap Tool 结果；
- LLM 使用、校验与降级原因；
- Variant、Trace、Action 和 BranchRule ID；
- graph/source revision。

答案组织层默认启用前必须在完整分享 Query 集上比较：

- Evidence Pack 证据覆盖；
- Query facet 和比较对象覆盖；
- 多方案分点完整率；
- `source_attribution`；
- `unsupported_claim`；
- `useful_answer_before_question`；
- `refusal_with_relevant_evidence`；
- 图片和附件绑定；
- 安全门、未知 ID 和错误解决声明；
- 调用成功率、校验失败率、降级率、时延、token 和成本。

Read Runtime v3 在 2026-08-04 的 shadow validation 上完成 60/60，0 个 contract
failure，verifier pass rate 100%，官方 answer/status 与冻结基线一致率 100%，冻结
清单评测前后都是 20/20 无 drift。该结果证明 shadow 契约与隔离跑通，不代表
bootstrap 已具备 Codex 根因锁定或多 Trace 语义编织能力。详细指标和迁移边界见
[读侧 Read Runtime v3 设计原理与取舍](读侧-Read-Runtime-v3设计原理与取舍.md)。

Read Runtime v4 的事故复测已覆盖真实诊断包的时间对齐、事件、调用栈、假设和行动计划。
当前 v4 仍保持 `ask_info` / `diagnosable=false` / `executable=false` 的安全边界；
答案可以给出低风险证据保全、诊断验证和修复后验证，但不会把候选假设升级为根因，
也不会将破坏性动作变成可执行命令。v4 的行动计划字段、风险门禁和校验说明见
[读侧 Read Runtime v4 证据调查管线](读侧-Read-Runtime-v4证据调查管线.md)。

## 10. 与写侧及 QA 项目的关系

读侧只消费：

- canonical KG_v2；
- 可重建 SAG_v2；
- 原文 Chunk 和媒体资产；
- 调用方提交的只读证据；
- DiagnosticSession。

写侧负责：

- 文档和群聊抽取；
- Section/FAQ/表格语义切块；
- KG 路径对齐；
- EvidenceItem、Variant、Trace 等对象构建；
- review 和入图；
- 增量更新后触发 SAG_v2 重建。

`qa_agentic_system/debug_agent` 使用 embedded snapshot。`debug_agent_system` 完成实现和
验证后，需要另行同步 snapshot，QA 项目的端到端行为才会变化；本读侧设计不直接修改其
旧 runtime 或 Supervisor Composer。

## 11. 设计边界

- 不把 Codex 作为 KG_v2 的第二事实源；
- 不让模型自由扫描整个文件系统或网络；
- 不让原文 Chunk 直接生成未经过 KG 安全门的执行 Action；
- 不用 Query 完整句子特判修复单个案例；
- 不用答案 Prompt 掩盖真正的召回缺失；
- 不因 `ask_info` 清空已有资料答案；
- 不因文档命中绕过高风险确认；
- 不在没有 `verified_fix` 时宣称已解决；
- 不要求安装第三方 Python 库才能运行确定性读侧。
