# 写侧：群聊知识入图 Pipeline

> 更新日期：2026-07-27
> 范围：Xing/飞书群聊与 text-only 历史消息进入 canonical KG v2 的写侧流程。
> canonical 图：`data/kg_v2`；`data/kg` 只保留兼容链，不是本文目标图。
> 读侧见 `docs/读侧-诊断检索-整体设计.md`。

## 1. 当前结论

群聊知识入图不是“让 DeepSeek 直接读聊天并生成 KG”，而是四层受控过程：

```text
原始消息与附件
  -> 恢复可审计的消息关系、episode、case 和 trace 候选
  -> 抽取来源约束的 Case/Action/Outcome 候选
  -> 本地规范化、质量门控和人工审批
  -> approved-only 增量合并与执行图/SAG 重建
```

当前状态：

1. W1、legacy W7、W2、W3、W4、W6、W5 已经形成 KG v2
   canonical queue 闭环。
2. legacy W7 仍是群聊生产候选的唯一权威语义整理器。
3. 新 W7 多决策 Agent 已完成两轮 shadow：
   `CaseBoundaryAgent + EvidenceAnchorAgent + W2 atomic-case adapter +
   SparseCandidateGraphBuilder + NeighborLinkAgent + TracePhaseAgent +
   OutcomeReconcilerAgent + TraceCompiler`。
4. shadow 结果固定
   `promotion_allowed=false`、`legacy_authoritative=true`，不会进入 W6/W5
   或修改 KG；主 Pipeline 也已能将同一 shadow 写入独立
   `w7_shadow/manifest.json`。
5. W6 trace review payload、correction events 和审批 hash 已落地；结构型
   correction 会持久化 W2 重抽取请求并在履约后重新回到 pending。完整 5 条
   校准、固定 173 回归和独立 acceptance 完成前，群聊不能切换到
   `assisted` 或 `multi_agent`。

## 2. 固定术语

群聊处理中必须区分以下层级：

| 术语 | 含义 |
|---|---|
| `message` | 一条原始消息；可能只有图片、附件或诊断包 |
| `reference_component` | 由平台原生或受约束推断关系形成的局部消息组件 |
| `session` | W1 的候选处理窗口，可包含多个并行问题 |
| `episode` | 一轮相对一致的故障阶段 |
| `case_item` | 可独立送 W2 的单一业务问题 |
| `trace_group` | 同一故障跨 episode、跨日期的纵向演化 |
| `trace_phase` | report、diagnosis、action、recurrence、validation 等阶段 |

`session`、`episode`、`case_item` 和 `trace_group` 不能互换。一个现场日报
可以是一个 session anchor，同时包含多个 case item；同一 trace 又可以跨越
多个 episode，并保留失败、短期恢复、复发和最终验证等不同 phase。

## 3. 当前生产链与目标链

### 3.1 当前生产候选链

```text
Xing/飞书 archive 或 text-only 消息
  -> W1 relation-aware collect
  -> legacy W7 ReviewContextAgent
  -> W2 native_v2 / prompt_first
  -> W3 deterministic normalization + shared TraceCompiler
  -> W4 typed/readiness/KG-v2 semantic gate
  -> W6 v2_typed_candidates 人工审核
  -> W5 approved-only merge
  -> KG v2 validator
  -> materialized execution + SAG 原子重建
```

所有新候选默认停在 W6。候选生成、W4 通过或 dry-run 成功都不等于已经入图。

### 3.2 目标 W7a/W7b 链

```text
W1 Source Ledger
  -> W7a
       CaseBoundaryAgent
       EvidenceAnchorAgent
  -> AtomicCaseEnvelope[]
  -> W2
       SourceCase / Fault / Action / Outcome facts
  -> 本地 SparseCandidateGraphBuilder
  -> W7b
       NeighborLinkAgent
       TracePhaseAgent
       OutcomeReconcilerAgent
  -> 本地 TraceCompiler
  -> W3 -> W4 -> W6 -> W5
```

模型只输出引用已有 message/case/trace ref 的 decision patch。本地程序负责：

- 完整消息记账；
- allowed ID 白名单；
- identity/strong/weak 候选图；
- 稳定 KG ID；
- 执行顺序与执行计数；
- Observation 和 BranchRule；
- schema/KG validator；
- content hash、幂等重放与回滚边界。

## 4. W1：来源证据与会话恢复

实现入口：

```text
src/debug_agent_system/agents/write/w1_chat_collect/
src/debug_agent_system/agents/write/w1_message_relations.py
```

W1 负责：

- 导入 Xing/飞书 archive、标准 messages JSONL 和 text-only 历史；
- 保留 message ID、chat、sender、时间、mention、原文和 source offset；
- 保留图片、视频、文件、Jira、日志、`.proj/.dmp/.dlog` 等附件元数据；
- 构建平台原生 reply/root/thread 关系；
- 生成受约束的 context/cross-window continuation 候选；
- 构造 relation-aware session 和 episode；
- 给消息分配 fault、diagnostic、action、resolution、context、noise 等粗角色；
- 输出 `messages.jsonl`、`thread_summaries.json`、`episodes.json` 和
  `run_manifest.json`；
- 不生成 KG 对象，不调用 W5。

### 4.1 硬关系与软关系

原生 `parent/root/thread/upper_message` 是 hard relation。推断的
`context_continuation` 与 `cross_window_trace_continuation` 必须作为
soft candidate 单独保存，经过设备、产线、Jira、附件 identity 和显式
cannot-link 约束后才能影响 episode。

禁止：

- 因时间接近就合并并行问题；
- 因群聊相同就视为同一 case；
- 因“相机/拍照失败”等常见词相同就视为同一 trace；
- 用推断关系冒充平台原生 reply；
- 为提高 completeness 把无归属 Jira/附件复制到全部 case。

### 4.2 附件证据

file/image/video 消息即使没有文字，也可能是故障首报或诊断起点。W1 必须
保留附件消息本身及相邻回复，不能只保留后续文字总结。

相同附件的高精度 identity 可以来自：

- 稳定 Lark file key；
- 已有 payload SHA256；
- 完整抓取且满足本地安全大小限制的内容 hash。

文件名相同、纯媒体重复或跨群复用不能单独构成 must-link。

## 5. legacy W7：当前权威语义整理

实现入口：

```text
src/debug_agent_system/agents/write/review_context.py
```

legacy W7 当前负责：

- 人员与 FAE 角色归因；
- 同 chat、Jira、附件和相邻上下文的 evidence 补全；
- 多故障日报的 `case_items[]` 拆分；
- fault focus 和 episode scope 修正；
- 动作、即时结果、观察、复发和最终验证信号整理；
- 区分短期恢复、失败、待验证、再次复发和明确 verified；
- 跨 session 生成
  `continuation_of/validation_of/recurrence_of/uncertain` 候选；
- 保留独立 phase，不把整个 trace 压成一个扁平 outcome；
- 判断 W2 readiness 与 block reason；
- 注入 KG/Gold 对齐背景，但只标记为 `alignment_only`。

legacy W7 的已知问题：

- 日报中真实故障仍可能停留在 `field_work_report`；
- 诊断包、图片先于文字问题时，起点可能被遗漏；
- 邻域召回与 Trace 组装耦合，容易形成大量弱边；
- 同 trace 和 phase 判断仍依赖较多词表/规则；
- “正常生产、未再出现”等结果可能未回连早期 case；
- 单次生成大 Trace JSON 时可能损坏、超长或 fail-closed。

这些问题是新 W7 小决策 Agent 的直接优化目标，不通过放宽 W4/W6 门禁解决。

## 7. W2：来源受限的知识抽取

实现入口：

```text
src/debug_agent_system/agents/write/w2_extract/
```

W2 从 W7 准备的 episode/case 输入中抽取 KG v2 候选。`native_v2` 和
`prompt_first` 支持 DeepSeek 直接输出完整 `CaseUnderstandingCard`，包括：

- fault family/variant；
- 原子 DiagnosticAction；
- `actual/recommended` 执行状态；
- ActionOutcome；
- 假设、根因、并存问题与次生问题；
- RequiredInfo；
- Trace 相关的来源语义。

本地代码继续负责：

- allowed message/evidence ID；
- strict schema；
- action 文本净化；
- Action–Outcome 完整性；
- `verified_fix` 无证据时安全降级；
- KG v2 对象与关系的机械映射。

W2 不负责人工批准，也不能因为模型给出高置信 JSON 就直接写图。

### 7.1 Action 准入

可进入 `DiagnosticAction` 的内容必须是可执行、可观察的原子步骤，例如：

- 导出/收集系统日志；
- 查询网卡重置事件；
- 检查日志时间空档；
- 重装网卡驱动；
- 更换扩展网卡；
- 验证生产恢复。

以下内容不能直接成为 Action：

- “麻烦老师看一下”；
- 整段日报；
- 单纯故障现象；
- 日志交接请求；
- 时间戳聊天记录；
- 只有疑问、没有动作的句子；
- 已经是 outcome/solution 的陈述。

W1 的结构化 `debug_actions` 仍必须经过 review-grade action 净化，不能被
W2 无条件信任。

## 8. KG v2 执行语义

群聊现场案例可形成以下对象：

```text
SourceCase
EvidenceItem
FaultFamily
FaultVariant
DiagnosticAction
ActionOutcome
DiagnosticTrace
TraceStep
ExecutionObservation
BranchRule
RequiredInfoSpec
```

其中：

- `DiagnosticTrace` 表示一条案例中的诊断/处置轨迹；
- `TraceStep` 记录 action 顺序、actual/recommended 和 attempt index；
- `ExecutionObservation` 记录实际执行次数、outcome 和 evidence；
- `BranchRule` 表达不同 outcome 后继续、监控、解决或未解决的去向；
- 执行对象由本地 TraceCompiler 生成或重建，不由 DeepSeek直接生成 KG ID。

W3 若合并、删除或重命名 Action，必须调用同一个 TraceCompiler 重建
TraceStep、Observation、Branch，避免动作列表和执行图漂移。

## 9. Outcome、状态与 resolved_by

必须区分两类状态：

### 9.1 ActionOutcome

常见案例级 outcome：

```text
verified_fix
ineffective
partial_temporary
mitigation_observed
pending_validation
diagnostic_method
context_not_root_cause
execution_failed
```

### 9.2 Trace resolution status

纵向 Trace 状态：

```text
unknown
pending
investigating
mitigation_observed
provisionally_resolved
ineffective
recurrence
verified
```

规则：

- 重启后暂时正常、目前正常、待观察最多是
  `provisionally_resolved/partial_temporary`；
- 后续再次复发必须修订更早的临时恢复；
- Jira Resolved/Done 本身不能证明现场 verified；
- “恢复生产、客户验证正常、原条件复测正常、明确未再复发”可作为
  verified 候选；
- verified 必须引用当前 intake 内明确 EvidenceItem；
- `resolved_by` 只允许由 `verified_fix` 和有效 evidence 支持；
- 高成本或破坏性动作即使历史有效，也必须在读侧要求人工确认。

失败尝试、诊断手段、短期缓解和待验证方案可以进入知识图作为历史 evidence，
但不能伪装成最终 Solution。

## 10. W3、W4、W6、W5 入图边界

### 10.1 W3：确定性规范化

W3 负责：

- family/variant/action 的 canonicalization；
- 重复对象和关系消解；
- actual/recommended 状态一致性；
- RequiredInfo 去重；
- Action ID 变化后的 TraceCompiler 重建；
- 不补造来源中不存在的事实。

### 10.2 W4：质量与 readiness

W4 同时检查：

- schema validity；
- typed provenance；
- 当前来源 evidence；
- family/variant/action/outcome 语义；
- action–outcome 完整性；
- verified evidence；
- `admission_target/admission_readiness`；
- `materialize_allowed/merge_allowed`。

案例 actual action 必须有执行状态、EvidenceItem 和 ActionOutcome。缺少关键
证据的候选只能 `route_review` 或 `reject`，不能为了提高 ready 比例降低门槛。

### 10.3 W6：人工审批

canonical 队列：

```text
data/kg_v2/review_queue/v2_typed_candidates.json
```

W6 只记录：

- review status；
- reviewer/note；
- approve/reject/request-more-info；
- candidate/content hash；
- dry-run diff 和 validator issue。

新 W7 完成后还需加入 case/trace 级 correction events。目前 legacy 审核和
release-gate 人工标注仍是主要人工边界。

### 10.4 W5：approved-only

W5 只应用已经在运行前批准的 review item：

- pending/rejected 不写图；
- W4 `reject` 永不写图；
- `route_review` 只有人工批准后才可合并，并保持原 materialization 限制；
- 相同 `dedupe_key + content_hash` 重放返回 `already_applied`；
- content/source hash 变化必须重新审核；
- 合并后运行 KG v2 validator；
- 一批图变化只统一 recompute/materialize/SAG build 一次；
- `--skip-sag-build` 必须显式返回 `index_stale=true`。

## 11. 一条群聊案例达到入图标准的条件

一条 case 不是因为“看起来完整”就能进入执行图。至少需要：

1. **边界正确**：没有把同一 session 的多个故障合成一条 case。
2. **证据完整**：首报、附件/诊断包、关键回复、动作和结果引用当前
   allowed message ID。
3. **Action 原子化**：每个 Action 是单一可执行步骤，不是日报、现象或协调话术。
4. **执行状态明确**：区分 recommended、planned、actual。
5. **Outcome 绑定**：actual action 有 EvidenceItem 和 ActionOutcome。
6. **状态保守**：短期恢复、待观察和 Jira Done 不升级为 verified。
7. **Trace 正确**：顺序、次数、phase、复发、validation 和分支可审计。
8. **W3/W4 通过**：规范化后仍满足 KG v2 validator。
9. **W6 人工批准**：批准绑定当前 candidate/content hash。
10. **W5 合并成功**：只通过 approved queue 增量写图并原子重建 SAG。

未达到 execution-ready 的案例仍可作为 `SourceCase/EvidenceItem` 或
support knowledge 进入相应审核范围，但不能进入读侧可执行策略。

## 12. Goldcase 与人工标注的地位

`data/annotations/goldcases` 是语义回归、校准和审核数据，不是自动入图指令。

- Goldcase 001–010：已有显式人工授权并进入 KG v2；其事实仍不能替代新
  intake 的当前 evidence。
- Goldcase 011–015：冻结的评测/回归集，`graph_ingestion=false`。
- Goldcase 016–020：开发回归集，`graph_ingestion=false`。
- 已用于 prompt、规则或实现修复的样本可以继续做 regression/calibration，
  但不能继续称为真正 blind。
- 最终 acceptance 需要来自未参与规则和 prompt 调整的新时间段导出。

人工审核应覆盖：

- fault focus；
- episode/case item 边界；
- multi-fault；
- resolution status；
- evidence message IDs；
- trace group/phase；
- W2 readiness；
- Action/Outcome/执行图修正。

### 14.2 multi-agent shadow

```bash
make w7-multi-agent-shadow
```

显式使用 `.env.local` 中的 DeepSeek key：

```bash
make w7-multi-agent-shadow W7_MULTI_AGENT_DEEPSEEK=1
make test-w7-multi-agent
```

在主 `WriteSidePipeline` 中注入 `w7_decision_client` 后，shadow 会随
`run_summaries()` 写入 `<out_dir>/w7_shadow/manifest.json`；未注入 client
时不会发起网络调用。shadow 目录只属于评测产物，不是 W6 queue，也不是入图授权。

固定集完成后，用独立 acceptance gate 汇总人工校准、173 条安全门和
held-out（缺少 held-out 默认 fail-closed）：

```bash
make w7-multi-agent-acceptance \
  W7_ACCEPTANCE_HELDOUT=data/results/w7_multi_agent_heldout/safety_gate.json
```
