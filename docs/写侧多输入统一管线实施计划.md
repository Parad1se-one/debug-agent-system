# 写侧多输入统一管线实施计划

> 更新日期：2026-08-03。本文同时记录已经落地的 canonical 写侧能力、
> W7 多决策 Agent 的目标结构和仍未完成的发布条件。历史运行结果只作为
> 基线证据，不代替当前代码与人工审核门禁。

## 1. 目标与当前结论

所有非 SOP 写侧输入最终收敛到同一条可审计、可幂等重放、
approved-only 的 KG v2 管线：

```text
来源专用 Agent
  -> WriteIntakeEnvelope / typed candidate
  -> W3 确定性规范化
  -> W4 typed/readiness/semantic gate
  -> W6 人工审核
  -> W5 approved-only 增量合并
  -> KG v2 validator
  -> Debug 术语层确定性重建
  -> 批次原子重建 materialized execution / SAG
```

当前结论分为三层：

1. **统一 ingress 与入图安全边界已落地。** 群聊、text-only、非 SOP
   文档、工具证据、专家修正、D1 和 D3 已有 typed/readiness 与
   `W4 -> W6 -> W5` 边界。
2. **文档版本化增量闭环已落地。** W9/W10 chunk manifest、内容变更重审、
   source-scoped replacement 和图变化后的批次级 SAG 原子重建已经实现。
   SOP 原始文档也已通过显式 `sop_document_incremental.v1` 契约进入同一
   approved-only 边界；旧 curated builder 只保留为显式 bootstrap/rollback。
3. **群聊 Trace 语义仍处于升级期。** 旧 W7 仍是唯一权威结果；新的 W7
   多决策 Agent 已接入主 Pipeline 的独立 shadow 产物目录，但仍不能进入
   W6、W5 或改写 KG。晋级由单独 acceptance gate 决定，不能用 shadow
   safety gate 代替。

因此，本项目当前不是“所有群聊都可以自动入图”，而是“多来源候选可以
安全地进入统一审核边界；执行图知识必须同时满足来源证据、W4、W6 和
Trace 语义门禁”。

## 2. 目标主链

### 2.1 群聊与 text-only

旧生产链暂时保持：

```text
W1 -> legacy W7 -> W2 -> W3 -> W4 -> W6 -> W5
```

目标链拆成 W7a 和 W7b：

```text
W1 Source Ledger
  -> W7a
       CaseBoundaryAgent
       EvidenceAnchorAgent
  -> AtomicCaseEnvelope[]
  -> W2
       Case / Action / Outcome 事实抽取
  -> 本地 SparseCandidateGraphBuilder
  -> W7b
       NeighborLinkAgent
       TracePhaseAgent
       OutcomeReconcilerAgent
  -> 本地 TraceCompiler
       DiagnosticTrace
       TraceStep
       ExecutionObservation
       BranchRule
  -> W3 -> W4 -> W6 人工审批 -> W5
```

DeepSeek 只能输出引用 allowed ID 的小型 decision/patch。消息完整记账、
候选图、稳定 ID、执行顺序、执行计数、分支、契约校验、图 diff 和回滚都由
本地确定性程序负责。

### 2.2 非 SOP 与 SOP 文档

```text
源文档
  -> source contract：raw_doc / sop_doc
  -> W9 复用读侧语义切块器
       原文 / offset / source hash / source section ID
  -> W10 绑定 draft KnowledgeSection ID
       document_layer + fault_mapping
  -> W3 -> W4 -> W6
  -> W5 原子版本替换
  -> validator -> SAG 原子重建
```

文档推荐动作和现场案例实际动作使用不同的质量契约：

- 文档动作必须有可追溯文档依据，不强制存在现场 `ActionOutcome`；
- 案例实际动作必须有执行状态、`EvidenceItem` 和 `ActionOutcome`；
- 文档不得伪造 actual Trace、现场 verified 或历史执行次数。
- `sop_doc` 必须携带 `sop_document_incremental.v1`，且 source ref 不得指向
  `data/kg_v2_sop_draft_build`；普通候选伪装 `source_kind=sop` 仍被 W4/W5
  拒绝。

### 2.3 KG v2 术语层刷新

所有 approved-only 合图在 schema 校验和文档关系刷新成功后，统一调用
`write_terminology_layer`。它将 Family、Variant、Action 及类别、子系统、设备、阶段
投影到 `DebugConcept / TermExpression / TermSense`。相同规范名称且
`action_role` 相同的 Action 实例复用一个 Operation 概念，但原 Action、Trace 条件和
安全约束保持不变。revision 和数量写入 W5 审计结果的 `terminology_refresh`。

未批准、W4 未通过、schema 非法或合图失败的候选不会刷新术语层。历史 `keywords`
只生成 `search_hint`；人工同义词、简称、旧称和错拼必须在
`data/kg_v2/terminology/curated_terms.json` 中审批后生效。完整契约见
`docs/Debug场景术语体系与KG_v2集成.md`。

approved-only 合图完成后，通过独立的
`make kg-v2-terminology-review-build` 治理任务重建
`data/kg_v2/review_queue/terminology_candidates.json`，不把第二次全图扫描塞进 W5
原子事务。生成器保留内容未变化的历史人工决策；候选证据变化时标记
`needs_re_review`。新候选和搜索提示不会自动生效，只有目标概念、关系类型、审核人
完整且决策不冲突的批准项，才可通过
`make kg-v2-terminology-review-apply` 导入人工术语表。

### 2.4 其他来源

```text
Jira / proj / dmp / 日志  -> TOOL + EvidenceContextParser --+
专家人工修正              -> Expert Review builder ---------+
D1 诊断反馈               -> evidence-only intake ----------+-> W3/W4/W6/W5
```

## 3. 不可破坏的统一约束

1. 来源 Agent 只负责来源语义，不直接决定写图或物理分区。
2. KG v2 增量候选使用唯一 canonical queue：
   `data/kg_v2/review_queue/v2_typed_candidates.json`。
3. W4 是 `decision`、`admission_target`、`admission_readiness`、
   `materialize_allowed` 的唯一机器决策边界。
4. W6 只记录审核与 correction，不直接写 KG。
5. W5 只读取已批准项；`pending/rejected/not_ready` 永不写图。
6. 只有 `execution_ready` 且通过执行语义 validator 的候选才能物化执行图。
7. gold case 和 KG alignment 只是风格/规范化背景，不能成为新候选的当前证据。
8. 相同 `dedupe_key + content_hash` 重放必须幂等；内容变化必须
   `needs_re_review`。
9. 人工修正生成 fresh/rebound candidate，不覆盖原候选或继承旧批准。
10. SOP 原始文档与非 SOP 文档共用版本化增量边界；curated build 目录继续
    被增量入口拒绝，旧 builder 只允许显式 bootstrap/rollback。
11. W7 模型 Agent 不得生成 KG 主键、绕过 W4/W6 或直接调用 W5。
12. W5 只有在一批批准项真实改变图后，才统一执行 validator、policy
    recompute、materialization 和 SAG 原子重建。

## 5. 文档 Chunk 与版本更新语义

W9 复用读侧 Section/FAQ/表格语义切块器，生成包含原文、block offset、
source hash、对齐关系和源 section ID 的未审批 `chunk_manifest`。

当前完整结构解析覆盖 `.docx/.md/.txt/.xlsx/.pptx`；`.pdf/.doc/.xls/.ppt`
没有可靠正文解析时固定进入 `review_only`，不会根据文件名猜测可执行动作。

W10 将源 section ID 绑定到 draft `KnowledgeSection` ID。完整 manifest
只进入 `document_layer` 审核项；`fault_mapping` 只携带引用，避免重复存储。

必须继续满足：

- pending/rejected chunk 不进入在线召回；
- 同路径内容变化生成新 bundle/content hash 并重新审核；
- W5 按 `dedupe_key + content_hash` 判断幂等重放；
- 新版本批准后 source-scoped 替换旧
  `KnowledgeDocument/KnowledgeSection/ProcedureStep/EvidenceItem`；
- source-scoped replacement 不自动删除共享 Family、Variant、Action 或
  已由其他来源支撑的执行对象；
- 文档层和 fault mapping 版本不一致时不得形成中间状态；
- CLI 在任意真实 KG v2 图变化后批次级原子重建 SAG，纯文档和
  support-only 批准也不能留下 stale index。
- `make kg-v2-build-curated` 已改为 SOP source sync，执行变更检测并停在 W6；
  `make kg-v2-build-curated-legacy` 仅用于已有备份前提下的 bootstrap/rollback。

旧的非 SOP 专项契约已作为阶段快照归档到
[`archive/write-side/20260730/非SOP增量写侧管线.md`](archive/write-side/20260730/非SOP增量写侧管线.md)。
本文是当前唯一的多输入写侧实施契约。

## 8. 完成与发布门禁

### 8.1 全来源共同门禁

- 所有支持来源都有专用入口、typed contract 和 canonical queue 证据；
- 没有来源绕过 W4/W6 直接触发 W5；
- pending/rejected/not-ready 写图数为 0；
- `dedupe_key + content_hash` 幂等率为 100%；
- source 或内容变化后的旧批准复用数为 0；
- KG v2 validator、materialization 和 SAG 重建全部成功；
- 文档/D1/D3 生成未观测 actual Outcome/Trace 的数量为 0；
- 未批准高成本或破坏性 Action 进入执行图的数量为 0。

### 8.2 W7 专项门禁

- stage schema valid：100%，或合法 fail-closed 且可单组件重试；
- TraceCompiler 幂等：100%；
- 核心高信号召回：不低于 98%；
- 诊断类高信号召回：不低于 95%；
- 附件起点召回：不低于 95%；
- 多故障拆分准确率：不低于 90%；
- must-link precision/recall：不低于 90%；
- cannot-link precision：不低于 95%；
- phase 顺序与 resolution status 准确率：不低于 90%；
- verified 无明确 evidence 的数量为 0；
- 当前 5 条 calibration strict gate 达到 5/5；
- 相比 legacy，每个 session 的人工 correction operation 数下降至少 50%。

### 8.3 灰度开关

```text
legacy              当前生产/回退模式
shadow_multi_agent  新旧并跑，只写评测目录
assisted            新结果预填 W6，人工批准前不影响后续
multi_agent         新 W7 成为候选生产者，legacy 保留回退
```

自动回退条件包括 stage schema invalid、source hash 变化、引用越界、组件
超过上限、TraceCompiler/KG validator 失败、模型超时或输出损坏，以及批准
hash 与待应用 bundle 不一致。
