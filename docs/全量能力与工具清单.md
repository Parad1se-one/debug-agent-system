## 11. 工具化观察与建议（面向下一步）

### 11.1 已存在的"工具化"层（可优先复用）

1. **`agents/tools/` 是唯一真正"工具化"的一层**：8 个 parser + 统一路由 `EvidenceToolAgent.parse` + `ReadEvidenceToolExecutor`（已有 envelope、只读标志、安全边界）——**建议作为全量工具化的基础设施**。
2. **`read_runtime_v3/providers.py ReadToolRegistry`** 已把 raw/kg/evidence 暴露为可迭代工具 schema，且 `execute` 返回统一信封——**只差把 incident 解析能力注册进去**。
3. **`adapters/codex_read/executor.py`** 已有 32 个工具白名单（含 25 个 incident 工具）——Codex 专用，可作 schema 蓝本。

full = build_full_registry(

### 12.5 与现有三处 schema 的关系

- `CorpusReadTools.schemas()` / `ReadToolRegistry.schemas()` / `read_side_tool_schemas()` 保留（向后兼容），**统一注册表是它们之上的聚合层**。
- 注册表执行结果统一为 `debug_agent_system.read_tool_result.v1` envelope（复用现有 `ToolResultEnvelope` 语义），带 evidence_ids / safety / observability。
- 完整后端装配（incident/KG/corpus）通过 `build_full_registry(...)` 注入，未注入的后端对应工具仍注册但执行返回 `backend_unavailable` 结构化失败。
